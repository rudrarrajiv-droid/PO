STEP 3 — STATUS TRANSITIONS
============================================================

Implement controlled status transitions.

A status must change ONLY through an approved action.

Do not allow the user to manually type arbitrary status values.

Do not allow:

INVALID STATUS

UNKNOWN STATUS

UNDEFINED STATUS

Do not allow jumping directly between statuses if Phase 23 did not
permit that transition.

============================================================
STEP 4 — MR VALIDATION BEFORE TRANSITION
============================================================

Before any MR workflow action:

validate all fields required for that specific action.

Example:

If completion requires certain fields:

those fields must be valid before completion.

If validation fails:

BLOCK THE ACTION.

Show the exact missing/invalid fields.

Do NOT partially complete the MR.

============================================================
STEP 5 — RM VALIDATION BEFORE TRANSITION
============================================================

Apply the same principle to RM.

Use ONLY the validation requirements defined in Phase 23.

If required information is missing:

BLOCK THE WORKFLOW ACTION.

Do not silently fill missing values.

============================================================
STEP 6 — EDIT CONTROL
============================================================

Implement the exact edit rules from Phase 23.

If a record is editable:

allow editing of only the fields permitted by the workflow.

If a record is locked:

disable editing.

Show a clear reason.

Do not silently ignore the user's action.

============================================================
STEP 7 — COMPLETION CONTROL
============================================================

Implement completion ONLY if Phase 23 explicitly defined completion.

============================================================
STEP 8 — CANCELLATION CONTROL
============================================================

Implement cancellation ONLY if Phase 23 explicitly defined it.

Before cancellation:

If no cancellation reason was defined:

DO NOT invent one.

============================================================
STEP 9 — DELETION CONTROL
============================================================

Use the delete rules already confirmed in Phase 23.

If deletion is allowed:

use confirmation.

If deletion is not allowed for a particular status:

block deletion.

Do not automatically convert deletion into cancellation.

Do not automatically cancel instead of deleting.

Do not invent reversal logic.

============================================================
STEP 10 — CALCULATED FIELD PROTECTION
============================================================

Any MR/RM field already identified as calculated in Phase 23 must not
be manually overwritten where the business rule says it is automatic.

If a calculated field is locked:

show it as read-only.

If a calculated field is editable according to the source:

follow the source.

Do not change formula behaviour.

============================================================
STEP 11 — USER ACTION PROTECTION
============================================================

Prevent accidental duplicate workflow actions.

Examples:

Double-click COMPLETE

Double-click CANCEL

Double-click SAVE

Double-click UPDATE

must not execute the operation twice.

Disable the action while the request is processing.

============================================================
STEP 12 — CONFIRMATION UI
============================================================

For destructive or irreversible actions explicitly defined by the
workflow, use the existing confirmation dialog.

The confirmation must clearly state:

WHAT WILL HAPPEN

WHICH RECORD IS AFFECTED

WHICH ACTION WILL BE PERFORMED

Do not use vague confirmation text.

============================================================
STEP 13 — ERROR HANDLING
============================================================

If a workflow operation fails:

DO NOT show success.

DO NOT change the UI to the next status.

DO NOT partially update the record.

Show a clear error.

Keep the record in its previous valid state.

============================================================
STEP 14 — CONCURRENT UPDATE PROTECTION
============================================================

If the application architecture supports safe concurrency handling:

use it.

The system must not allow two users/actions to accidentally overwrite
each other's MR/RM status changes.

If concurrency handling is not already supported:

DO NOT introduce a large new architecture in this phase.

Report the limitation instead.
