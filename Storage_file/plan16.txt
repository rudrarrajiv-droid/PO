============================================================
PHASE 7 OBJECTIVE
============================================================

Implement ONLY:

PO OUT TRANSACTION

The user must be able to record material going OUT against an existing PO.

When an OUT transaction is created:

1. Create one OUT transaction.
2. Update total OUT quantity.
3. Recalculate Closing Balance.
4. Update Value according to the already approved PO logic.

Do NOT change the PO master information.

============================================================
STEP 1 — OUT ACTION
============================================================

Add an OUT action to the existing PO interface.

The action must operate against a selected existing PO.

Do NOT create a separate OUT module/page.

Do NOT redesign the PO page.

============================================================
STEP 2 — OUT FORM
============================================================

The OUT form must contain:

DATE

QUANTITY

REMARKS

Required.

Quantity:

Required.

Optional.

PO NO.

The user must NOT manually edit these fields.

============================================================
STEP 3 — OUT QUANTITY VALIDATION
============================================================

OUT quantity must:

- Be numeric
- Be greater than 0
- Reject negative numbers
- Reject invalid text
- Reject empty quantity

Do not save invalid data.

============================================================
STEP 4 — AVAILABLE BALANCE
============================================================

Before saving OUT:

Calculate the currently available PO quantity.

Use:

AVAILABLE BALANCE
=
OPN QTY + TOTAL IN - TOTAL OUT

Example:

OPN QTY = 1000

TOTAL IN = 200

TOTAL OUT = 100

AVAILABLE BALANCE = 1100

If user enters:

OUT = 300

then:

New TOTAL OUT = 400

New CLOSING BAL = 800

============================================================
STEP 5 — INSUFFICIENT BALANCE PROTECTION
============================================================

NEVER allow OUT quantity greater than available balance.

Example:

Available Balance = 500

User enters:

OUT = 600

BLOCK THE TRANSACTION.

Show clearly:

INSUFFICIENT PO BALANCE

Available:
500

Requested:
600

Short:
100

Do NOT save the transaction.

Do NOT allow negative Closing Balance.

============================================================
STEP 6 — SAVE OUT TRANSACTION
============================================================

When user clicks:

SAVE OUT

Create ONE transaction in:

poTransactions

with:

transactionType = OUT

and the selected PO reference.

Store:

PO reference

Date

Quantity

Customer

Item

User

Remarks if provided

Follow the existing project's audit/timestamp pattern.

============================================================
STEP 7 — DUPLICATE SUBMISSION PROTECTION
============================================================

If the user clicks SAVE OUT multiple times quickly:

Only ONE intended transaction must be created.

Prevent duplicate submission.

Do NOT create duplicates and then delete them.

============================================================
STEP 8 — RECALCULATE OUT QTY
============================================================

OUT QTY must represent:

SUM(all valid OUT transactions for that PO)

Do not allow the user to manually overwrite total OUT QTY.

============================================================
STEP 9 — RECALCULATE CLOSING BALANCE
============================================================

Use:

CLOSING BAL
=
OPN QTY + TOTAL IN - TOTAL OUT

Example:

OPN QTY = 1000

IN = 500

OUT = 300

Expected:

CLOSING BAL = 1200

============================================================
STEP 10 — VALUE
============================================================

Use the already approved PO VALUE calculation.

Do NOT invent a new formula.

Do NOT change Rate.

Do NOT modify OPN QTY.

If the approved calculation is based on:

CLOSING BAL × RATE

use that logic.

If another previously approved calculation exists, preserve it.

============================================================
STEP 11 — TRANSACTION SAFETY
============================================================

The OUT operation must not leave the database in an inconsistent state.

If saving the transaction and updating the related PO state cannot be
safely handled using the existing architecture:

STOP and report the issue.

Do NOT create a partial transaction.

Do NOT show success when the operation was not completed successfully.
