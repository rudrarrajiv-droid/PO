STEP 1 — ADD NEW PO UI
============================================================

Use the existing PO Management page and existing application UI
components.

The Add New PO form must contain ONLY these business fields:

1. PO NO.
2. PO DT
3. DELIVERY DATE
4. CUSTOMER NAME
5. CONSIGNEE
6. ARTWORK NO.
7. ITEM NAME
8. SIZE
9. RATE
10. OPN QTY

Do NOT add unnecessary fields.

IN QTY:

Do NOT ask the user to manually enter it during PO creation.

For a newly created PO:

IN QTY starts at 0.

OUT QTY starts at 0.

CLOSING BAL is calculated by the system.

VALUE is calculated by the approved PO business logic.

============================================================
STEP 2 — FIELD BEHAVIOUR
============================================================

PO NO.

Required.

Treat it as a business identifier.

Do not automatically generate a random PO number unless the existing
business workflow explicitly requires automatic generation.

PO DT

Required date.

DELIVERY DATE

Required date unless the existing source/business process clearly allows
it to be blank.

CUSTOMER NAME

Required.

CONSIGNEE

Optional unless existing business rules require it.

ARTWORK NO.

Optional unless the source/business process requires it.

ITEM NAME

Required.

SIZE

Optional unless the source/business process requires it.

RATE

Numeric.

Must not accept invalid text.

OPN QTY

Numeric.

Must be greater than or equal to 0.

============================================================
STEP 3 — FORM VALIDATION
============================================================

Before saving:

Validate required fields.

If a required field is missing:

Do NOT save.

Show a clear field-level validation message.

Do NOT use vague messages such as:

"Something went wrong."

Tell the user exactly what is missing.

Examples:

"PO No. is required."

"PO Date is required."

"Customer Name is required."

"Item Name is required."

"Opening Quantity must be a valid number."

============================================================
STEP 4 — NUMERIC SAFETY
============================================================

RATE must be stored as a numeric value.

OPN QTY must be stored as a numeric value.

Do NOT store them as formatted strings.

Do NOT save:

"₹500"

as the numeric value.

Store the appropriate numeric representation.

Formatting should happen only in the UI.

============================================================
STEP 5 — INITIAL PO VALUES
============================================================

When a new PO is created:

IN QTY = 0

OUT QTY = 0

CLOSING BAL must initially represent:

OPN QTY + 0 - 0

Therefore:

CLOSING BAL = OPN QTY

Do NOT ask the user to type Closing Balance.

============================================================
STEP 6 — VALUE
============================================================

Use the approved PO Value business logic identified during earlier
inspection.

Do NOT invent a different formula.

If the previously inspected workbook/business logic clearly establishes:

VALUE = CLOSING BAL × RATE

then use that approved logic.

If the earlier inspection found ambiguity about VALUE:

STOP before implementing this calculation and report the ambiguity.

Do NOT silently guess.

============================================================
STEP 7 — SAVE
============================================================

When the user clicks:

SAVE PO

perform validation first.

If validation passes:

Create ONE new PO document in the PO collection created in Phase 3.

Do not create duplicate PO documents from a single click.

Prevent accidental double submission if the user clicks Save multiple
times quickly.

Use the existing project's established Firestore service/repository
pattern.

Do NOT create a second database architecture.

============================================================
STEP 9 — AFTER SUCCESSFUL SAVE
============================================================

After successful save:

Show a clear success message.

Close the Add PO form/modal if that matches the existing application
pattern.

Refresh/reload the PO table using the existing page architecture.

The newly created PO should be visible.

Do NOT implement search or filtering in this phase.

============================================================
STEP 10 — FAILURE HANDLING
============================================================

If Firestore save fails:

DO NOT create partial data.

Show a clear error.

Do NOT pretend the PO was saved.

Do NOT retry indefinitely.

If the save result is uncertain:

STOP and inspect the database state before attempting another save.

This is important to prevent duplicate POs.

============================================================
STEP 11 — DUPLICATE PO PROTECTION
============================================================

Before saving, inspect the existing PO database structure and the
business meaning of PO Number.

If PO Number is intended to be unique:

prevent duplicate PO Numbers according to the safest implementation
supported by the existing architecture.

Do NOT silently overwrite an existing PO.

If duplicate behaviour is ambiguous:

STOP and report it instead of guessing.
