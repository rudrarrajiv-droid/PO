============================================================
PHASE 6 OBJECTIVE
============================================================

Implement ONLY:

PO IN TRANSACTION

The purpose is to record material received against an existing PO.

When an IN transaction is created:

- A new IN transaction is saved.
- PO IN QTY updates automatically.
- PO CLOSING BAL updates automatically.
- PO VALUE updates according to the approved business logic.
- Existing PO master information remains intact.

============================================================
STEP 1 — IN ACTION
============================================================

Add an IN action to the existing PO Management interface.

The action must be available for an existing PO.

Do NOT add IN fields to the main PO creation form.

IN is a separate transaction.

============================================================
STEP 2 — IN FORM
============================================================

The IN form must contain only the information required to record an
IN transaction.

Required:

DATE

QUANTITY

Optional:

REMARKS

The selected PO must already be known from the PO on which the IN action
was initiated.

Do NOT ask the user to manually re-enter:

PO Number
Customer
Consignee
Artwork
Item Name
Rate
Size

These already belong to the selected PO.

============================================================
STEP 3 — AUTOMATIC PO INFORMATION
============================================================

When opening IN for a PO, show read-only information:

PO NO.

CUSTOMER NAME

ARTWORK NO.

ITEM NAME

OPN QTY

CURRENT IN QTY

CURRENT OUT QTY

CURRENT CLOSING BAL

This information must come from the selected PO.

The user must not edit these fields from the IN form.

============================================================
STEP 4 — IN QUANTITY VALIDATION
============================================================

IN quantity must:

- Be numeric
- Be greater than 0
- Reject invalid text
- Reject negative numbers

Do not save an invalid quantity.

Show a clear validation message.

============================================================
STEP 5 — SAVE IN TRANSACTION
============================================================

When the user clicks:

SAVE IN

Create ONE new transaction in:

poTransactions

with:

transactionType = IN

and the selected PO reference.

Store:

PO reference
Date
Quantity
Customer
Item
User
Remarks if provided

Follow the existing project's timestamp and user/audit conventions.

Do NOT create duplicate transactions from repeated clicks.

============================================================
STEP 6 — RECALCULATE IN QTY
============================================================

After successful IN transaction:

TOTAL IN QTY must be calculated from the PO's IN transactions.

Do NOT manually overwrite the PO's historical transaction data.

The main PO record must reflect the current total IN.

Expected logic:

IN QTY = SUM(all valid IN transactions for that PO)

============================================================
STEP 7 — CLOSING BALANCE
============================================================

After IN:

CLOSING BAL must reflect:

OPN QTY + TOTAL IN - TOTAL OUT

Example:

OPN QTY = 1000

Previous IN = 200

New IN = 300

OUT = 100

Expected:

IN QTY = 500

CLOSING BAL = 1400

Do not allow the user to manually edit Closing Balance.

============================================================
STEP 8 — VALUE
============================================================

Use the VALUE logic already established during the earlier PO
implementation/inspection.

Do NOT invent a new formula.

If the approved logic is:

CLOSING BAL × RATE

then use it.

If the approved business logic is different, follow that approved logic.

Do not change the Rate.

============================================================
STEP 9 — TRANSACTION ATOMICITY
============================================================

The IN operation must not leave the database in a partially updated
state.

If the transaction is saved but the related PO calculation/update fails:

handle the failure safely according to the existing Firestore
architecture.

Do not silently report success when the operation is incomplete.

If transaction consistency cannot be guaranteed with the current
architecture:

STOP and report the issue before implementing.

============================================================
STEP 10 — DOUBLE SUBMISSION PROTECTION
============================================================

If the user clicks SAVE IN multiple times quickly:

Only ONE intended transaction must be created.

Prevent accidental duplicate IN records.

Do not solve this by deleting duplicates afterward.

Prevent them at submission level.

============================================================
STEP 11 — MAIN TABLE UPDATE
============================================================

The existing PO table must immediately show updated:

IN QTY

CLOSING BAL

VALUE

Do not reload the entire application unnecessarily.
